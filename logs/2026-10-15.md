- `git rev-list --count main..HEAD` / `HEAD..main` で分岐の進み具合を数値で確認できる
- `git diff --name-status main...HEAD`（3点リポジトリ記法）で「分岐元から見た差分」を確認できる

**理解深化：**

- Firestore は単一フィールドの `where` クエリに複合インデックスは不要（`orderBy` を併用した時に必要）。作った複合インデックスは過剰だった
- Firestore ルールは `read, write` と `read, update, delete` + `create` 分離の2通りで書けるが機能的に同等

**トラブルシューティング：**
- 「学習用に記憶から再実装したコード」と「本番リポジトリの完成版」が別物になっていた → 成果物は main が上位互換。学習ログと成果物は分けて扱う

- 主要コード（main の Firestore ルール：権限を操作別に分離）：
```rules
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /sessions/{sessionId} {
      allow read, update, delete: if request.auth != null
        && request.auth.uid == resource.data.userId;
      allow create: if request.auth != null
        && request.auth.uid == request.resource.data.userId;
    }
  }
}
```

- `git rev-list --count main..HEAD` / `HEAD..main` quantifies branch divergence
- `git diff --name-status main...HEAD` (three-dot notation) shows the diff from the merge base
- Leaving a feature branch idle hides upstream refactors (hooks split, added tests) from you

**Deeper Understanding:**
- Always check where a work branch forked before merging. Merging a branch cut from an old base rewinds main's improvements (`page.tsx` 55 → 388 lines, removing `export`s that tests import)
- Untracked files that collide with main's tracked files make `git checkout` fail → stash/move them before switching
- Firestore needs no composite index for a single-field `where` query (only when combined with `orderBy`); the one I created was unnecessary
- Firestore rules can be written as `read, write`, or split into `read, update, delete` + `create`; functionally equivalent

**Troubleshooting:**
- The from-memory recall code and the production repo's finished code are different artifacts → main is the better product. Keep learning logs and deliverables separate
