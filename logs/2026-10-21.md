### 💡 学びのポイント
**新規習得：**
- `Date.prototype.toISOString()` は常に **UTC** を返す。日本（UTC+9）では 00:00〜08:59 の間、UTC では前日になる
- ローカル日付を作るときは `getFullYear()` / `getMonth()` / `getDate()` を使う。`getMonth()` は 0 始まりなので +1 する
- テストは実行環境のタイムゾーンに依存させない。CI（GitHub Actions）は UTC で動くため、JST 前提のテストは落ちる

**理解深化：**
- 日付は「どの基準（UTC / ローカル）で扱うか」を1箇所に決めないと、フォームとカレンダーでズレる。共通関数に寄せると再発しない
- タイムゾーン依存のテストは「ローカルの時刻を指定して Date を作る」と環境非依存にできる

**トラブルシューティング：**
- 早朝 6:35 JST にフォームの初期日付が前日になっていた → `toISOString()` が UTC だったのが原因
- 最初に書いたテストは「UTC とズレること」を直接検証していて CI で落ちる危険があった → ローカル日付の境界（0:00 / 23:59）で検証する形に変更
- 草カレンダー側は元々ローカル基準だったため、フォーム側を合わせて統一した

export function toLocalDateString(d: Date = new Date()): string {
  const year = d.getFullYear();
  const month = String(d.getMonth() + 1).padStart(2, "0");
  const day = String(d.getDate()).padStart(2, "0");
  return `${year}-${month}-${day}`;
}

**Deeper Understanding:**

- Timezone-dependent tests can be made environment-independent by constructing `Date` values from local components
